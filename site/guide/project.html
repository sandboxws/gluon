Attaching to the module you are standing in

A REPL that reaches only the standard library is a toy. {% cmd ":use" %} attaches the session to a Go module — or start with gluon -host . — and then its packages import, including the ones under internal/, which is usually the interesting half.

{% session "project-use" "in ~/src/shop, a small service with an API, a database and a gRPC server" %}

The project in these guides is a small shop service: an HTTP API on chi, a gRPC server, a SQLite database behind sqlx, viper settings, a cobra CLI. Its source is in gluon's repository under testdata/shop, so every session here can be typed again against the same code.

Go allows a package under internal/ to be imported only by code under the path above it, so a module named gluon.local/session could never reach example.com/shop/internal/pricing. The rule is a prefix test on the importer's path, so gluon gives its temp module a path underneath the host's, and the test passes. It costs nothing a line: gluon still builds a one-file module, and the toolchain loads the import graph, not every package the project has.

Attaching changes what a bare name means — pricing is the project's — which is why it is asked for rather than automatic. {% cmd ":use" "-off" %} detaches. gluon doctor reports what attaching would see: the module, its go directive and every package a session could import.

2

Where a line runs

Attaching makes the project's packages importable. It does not move the program: every line runs in the session's own directory, so a path your code opens relative to where you started gluon is not found there.

{% session "project-cwd" %}

That is deliberate. gluon never writes into your project, and a line that creates a file would otherwise create it in your working tree, on every replay. The way code finds its files in production is the way it finds them here — an environment variable, a flag's default, a path resolved from a known root. The shop reads $SHOP_CONFIG, and resolves the paths in its settings against that file.

3

After you edit it

The session keeps what it derived from the project — the type checker's export data, the import cache, cached results — until you say the project changed. {% cmd ":reload" %} says so, and {% cmd ":watch" %} says it for you.

{% session "project-reload" "the tax rate edited in another window, between the two lines" %}

:reload drops every cached result and re-reads the project, and the next line is built against the source as it now is. :watch on polls the project's Go files and reloads when one changes; a change seen while a line is running waits until it finishes, and goes behind anything you typed ahead.

4

Adding a module

the only command that fetches

For anything the project does not already require, {% cmd ":get" %} adds a module to the session. It is the one command that fetches a module, and bare, it lists what the session can build against.

{% session "project-get" %}

A module added with :get belongs to the session, never to the project: gluon does not edit your go.mod. Its packages are what their names mean from then on, ahead of any package of the same name elsewhere in your module cache. Adding one can activate a plugin — toml above, whose {% cmd ":toml" %} writes a value as the document its tags produce; Plugins has all of them — and :get toml works too, because a plugin's short name is an alias for its module.

{% cmd ":get" "-rm" %} drops a requirement and fetches nothing. It is refused while an entry still imports the module, naming the entry, and refused for a module the project itself requires. Without a version, :get takes the latest; with one, that version.

5

The environment, and the config files

{% cmd ":env" %} is the process environment, and {% cmd ":conf" %} a project config file — TOML, YAML or JSON — both with anything shaped like a secret masked.

{% session "project-env" %}

A value is hidden because of its shape, never because of its key's name: a bearer token, a password in a connection string, a vendor-prefixed key. PASSWORD_HINT=ask the team is not a password, and a redactor that hid it would be one people learn to work around — so the footer says how many values were hidden and that this is a judgement by shape, not a guarantee. A secret is never shown in part.

6

Requests

{% cmd ":http" %} issues a request and renders what came back — the shorthand for the http.Get a line could always make.

{% session "project-http" "the shop's API, served on 127.0.0.1:8765" %} {% shot "http" %}

The method takes any case, and completes. {% cmd ":http" "-H" %} adds a header and repeats for another, {% cmd ":http" "-d" %} is the body, and {% cmd ":http" "-t" %} how long to wait. Quote anything with a space in it: no shell has been near the line. A header may name a variable rather than carry one — -H 'Authorization: Bearer $TOKEN' resolves $TOKEN in the program that sends it, so the value reaches no history file, and a header whose value is shaped like a credential is refused, because by then it is already in the history.

A request made on a line is made again on every line after it, like any effect. :http is a command, not an entry, so it runs once, when you type it. gRPC has the same shape in {% cmd ":grpc" %}.
