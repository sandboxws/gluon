How fast

testing.B

{% cmd ":bench" %} runs an expression through a real testing.B — the numbers go test -bench would give for the same expression, without the test file.

{% session "measure-bench" "one expression, five runs, two side by side, two CPU counts" %} {% shot "bench" "two expressions side by side, in a terminal" %}

B/op and allocs/op are always reported; there is no -mem flag, because there would be nothing for it to turn on. The flags say how the benchmark is run, never what is measured, and they are read only while they lead — everything from the first word that is not one of them is the expression, verbatim.

{% cmd ":bench" "-count" %} runs it more than once and reports the spread, which is what lets a number be trusted or distrusted. It gives the minimum, median and maximum rather than a standard deviation: at five runs a deviation is computed from too few samples to mean what a reader assumes, and these three numbers were all actually seen.

Two expressions separated by a comma are measured side by side, with the ratio between them — the comparison you would otherwise run twice and hold in your head. Both run in one evaluation, so neither is timed against a different replay of the session, and a comma inside brackets, braces or a literal is not the separator. A quantity that is zero on the left has no ratio, and says so rather than printing an infinity.

{% cmd ":bench" "-cpu" %} runs once per GOMAXPROCS value and labels each, the one way to see a contention effect from a prompt. {% cmd ":bench" "-profile" %} keeps the run's CPU profile and prints the command that opens it. It goes into the session's own temp directory: gluon never writes into your project.

Where the time went

pprof

:bench says how much. {% cmd ":profile" %} says where: it runs the expression once with the CPU profiler on and ranks the functions that took the time, naming the session entry and the line each came from. {% cmd ":memprof" %} does the same against the heap.

{% session "measure-profile" "a CPU profile and a heap profile, from real runs" %}

Read the sample count first. It is the number that says whether the ranking under it means anything, and for a REPL expression it often does not. Go asks for 100 samples a second, so an expression that finishes in a hundredth of a second contributes none, and the report is empty by construction. Below a hundred samples the leading share carries more than ten percent of error and can swap places between two runs of the same expression — which is why the report says so rather than letting a ranking speak for itself.

That threshold is further off than the arithmetic suggests. The loop above ran for a little over half a second — fifty-odd samples at the rate Go asks for — and 38 came back, because the rate is what the profiler asks the operating system for, not what it gets; macOS in particular delivers a fraction of it. Profile a workload, not a line, and believe the count over the clock.

A heap profile carries four measures that answer different questions, so :memprof names the one it shows — allocated bytes, which pairs with the B/op :bench prints — and leaves the other three in the file. What the summary cannot tell you, the file can: go tool pprof opens it, and -http=:0 draws the flame graph gluon does not try to. Neither command takes a port: each line is a program that runs and exits, so there is no live process to serve a profile from, and these capture one from a run that really happened instead.

What the compiler decided

builds, never runs

Escape analysis, inlining and the assembly listing are answered by the compiler itself, in its own words rather than a paraphrase. Each costs a build and never runs anything.

{% session "measure-compiler" %} {% shot "compiler" %}

{% cmd ":esc" %} asks whether a value reaches the heap, and the answer depends on context — which the output says every time. The same 32-byte slice stays on the stack while nothing keeps it, and escapes the moment it is handed to fmt.Sprint as an any. For the flatter question, does this allocate, :bench's allocs/op is the better answer: it is measured, and context does not change it.

{% cmd ":inline" %} reports, for a line, every call the compiler flattened, and for a function you declared, whether it can be inlined at all and what it costs against the budget. fizzbuzz cannot: its cost is more than three times what the compiler allows.

{% cmd ":asm" %} is the listing for one function or method the session declared — F, T.M or (*T).M — with every position naming the entry it came from. Only the session's own functions: widening the listing to the standard library would recompile it under different flags and throw away the warm build cache every line depends on, so :asm strings.Index is refused with that reason rather than answered slowly. This one is arm64, because that is where it was recorded.

Vet and the race detector

{% cmd ":vet" %} runs the toolchain's own analysers over the session, and {% cmd ":race" %} runs one expression under the race detector.

{% session "measure-vet" %}

:vet reports each finding against the line you typed; with an expression, it vets the session with that line added. Findings in the code gluon generates around your lines are never shown, because there is nothing you could do about one. It vets the session, not the module you are attached to — that has its own go vet ./... — and there is no :lint, because staticcheck and its neighbours are dependencies gluon does not have.

:race is the one question here that has to run, because a data race is a runtime fact no build can be asked about. The value is printed either way: a race is something that happened during the run, not instead of it. It observes one run — finding nothing is not proof there is no race, since the detector sees one interleaving, and the output says so every time rather than implying a verdict it cannot give. The first :race in a session builds an instrumented binary beside the ordinary one, and the first on a machine compiles the race-instrumented standard library as well, which takes a few seconds; later ones reuse both.

5

The stack

{% cmd ":trace" %} evaluates an expression and captures the stack it was evaluated on, each frame named by the session entry it came from.

{% session "measure-trace" %}

It holds the expression's callers, not its callees — a function it is about to call has not been entered yet, and by the time the call returns its frame is gone. At the prompt the chain is usually one line long, and the output says why rather than showing an empty list: gluon compiles each line into a program whose main runs it directly, so there is no process to pause and no breakpoint to set. For what a call does underneath, :save -debug writes the session out as a module with a debugger launch configuration beside it, and names the command that starts one — Scratchpads has it.

Where a line's latency goes

{% cmd ":time" %} on makes every line report where its latency went: gofmt, the type check, the build and the run.

{% session "measure-time" %}

The two lines are the whole design, measured. The first had to run, so it paid for the build and the run — a few hundred milliseconds, which is the price of the real compiler. The second has a type error, which the in-process checker found in about a millisecond; nothing was built. The same is true of declarations, constant expressions, and every question on the inspecting page that is marked no build. How it works has the numbers for each kind of line.
