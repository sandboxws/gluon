The program your session became

A session is a list of entries — the lines you typed — and every line renders all of them into one Go program, builds it and runs it. {% cmd ":src" %} shows that program, exactly as the compiler saw it.

{% session "session-src" %}

Everything gluon does to your lines is there to read: the import it added, the _ = x that keeps Go from calling x unused, it rewritten to the _1 it meant, and the call that prints the last value. Nothing is hidden, so when a line does something you did not expect, the program it ran is one command away. A long program opens in a view at the prompt and prints whole through a pipe.

2

Every line replays — and what that costs

the honest limitation

Because every line re-runs the whole session, side effects repeat: a request fires again, a file is written again, time.Now() moves on and rand changes its mind. Output from the replayed lines is muted, so you only see the newest line's — but the re-execution is real.

{% session "session-pin" "a line with an effect, and :pin" %}

Each len(b) is one larger than the last, because each line ran hit() again. {% cmd ":pin" %} is the defence: it takes an entry out of the program — you are saying it has already happened — so replay stops running it. {% cmd ":pin" %} on its own lists what is pinned, and {% cmd ":hist" %} marks it.

A pin is refused when a later entry uses what the pinned one bound, and says which entry that is. gluon does not invent the missing value: the printer writes a display form, not a literal — a uint8 reads 195 (0xc3) — so rebuilding a value from what was printed would be a guess, and a guess here is a wrong answer that looks like a right one.

{% cmd ":refresh" %} runs the program once with every pin lifted and puts the pins back — for when the code under a pinned entry changed and the result it holds is stale. {% cmd ":unpin" %} puts an entry back for good: unpinning replays the session, and so does every line after it, which is why the count moved by two.

3

Editing the entries

{% cmd ":hist" %} numbers the entries, {% cmd ":drop" %} removes one by its number, {% cmd ":undo" %} removes the last, and {% cmd ":reset" %} removes them all.

{% session "session-edit" %}

A removal that would leave the session unable to build is put back, with the reason: c reads b, so b stays. :drop is also refused when a later line reads it, or an _N the removal would renumber, because that line would silently start meaning something else.

{% cmd ":reset" %} clears the entries and keeps the modules you added, so trying the same library a different way does not fetch it again; {% cmd ":reset" "-deps" %} clears both. u in vim mode, by the way, undoes typing, not entries: the two share a name and nothing else. Editing has the keys, and {% cmd ":edit" %}, which edits every entry at once.

4

Snapshots

{% cmd ":bookmark" %} records the session under a name and takes nothing away from it. {% cmd ":restore" %} puts one back and replays it. {% cmd ":branch" %} is a bookmark for when you had not decided to take one.

{% session "session-bookmark" %}

:branch with no name makes one up and prints it, because having to invent a name is the thing it exists to remove — the state before an experiment is recoverable without having thought of it first. A snapshot holds the entries, their order and what is pinned.

A restore that fails to replay puts back the session you were leaving and says so: a restore that could destroy the state it was moving away from would be worse than none. Snapshots last for this session and never reach the disk. Scratchpads are what make a session durable.

5

Yesterday's lines

ctrl-r walks the history file a line at a time and {% cmd ":hist" %} numbers the session; neither gets you the expression you had right in yesterday's session. {% cmd ":replay" %} searches the whole file and brings the matches in.

{% session "session-replay" %} {% shot "keys-search" "ctrl-r, searching for bench" %}

The matches are shown before any of them runs. A history line is a line somebody typed, some of them wrote something, and the session replays every entry on every later line — so what is about to happen is printed verbatim rather than counted. enter in the view brings them in, q leaves without running anything, and {% cmd ":replay" "-run" %} is the form to type when you already know what the pattern matches — and the form a pipe has. Meta commands are skipped: replaying a :reset would clear the session it was being replayed into.

6

From a file, and into a test

{% cmd ":load" %} reads a file in, a construct at a time, as though each were typed. {% cmd ":test" %} goes the other way: it writes the expression you just checked, and the value you judged right, down as a Go test.

{% session "session-load" %}

:load stops at the first construct that fails, and leaves out an unfinished one at the end rather than reporting against text that may still be being written. The file is read once; :load it again after changing it.

You tried an expression, looked at the answer and decided it was right. That is got, want and a judgement — the whole content of a Go test — and gluon already holds the expression, its type and its value, so :test writes it, carrying the locals the expression needs. The doc comment says the expectation is what was observed, not what is correct; that judgement stays yours, which is why it prints rather than writes. {% cmd ":test" "-table" %} shapes it so a second case can join, :save -test keeps what was generated, and a value with no literal form — a pointer, a channel, a func — is refused with the part that caused it rather than emitted as a test that does not compile.

7

Goroutines

A go statement on its own would print nothing: main returns before the goroutine is ever scheduled. So gluon waits briefly for the goroutines your lines started — and says that it did, because a real main would not have.

{% session "session-goroutines" %}

The wait is bounded at two seconds, and a goroutine still running at the deadline is reported rather than waited on for ever. It covers the goroutines the session's own code started: a library keeps goroutines of its own for as long as the value that owns them — database/sql one per open *sql.DB — and those are left alone, as a real main would leave them. When nothing was started, nothing is said.
