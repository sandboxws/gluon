Static tools

Served by a bare gluon mcp. Each answers from go/types or the transcript and never builds or runs anything.

go_typeis :t

the type of an expression      (Ruby's .class)

Answers from go/types in gluon's own process, so it never builds and comes
back in about a millisecond.

-d is the exception: it reports the dynamic type — what is actually inside
an interface value — which nothing but a run can know. It costs a build and
an execution, and it runs your expression, so a call with a side effect has
it. Only at the prompt: the MCP tool stays static and ignores the flag.

expr reads: [-v | -d] <exp>

Flags, written into expr as at the prompt:
  -v  add the underlying type and its kind
  -d  run it once for the dynamic type inside an interface (only at the gluon prompt; this tool ignores it)

Examples (expr):
  "strconv.Atoi(\"12\")" — two values: (int, error)
  "-v time.Second" — the named type, what it is underneath, and its kind

The -d form runs the expression and is available only at the gluon prompt. This tool is static: a leading -d is ignored and the static answer is returned.

go_mockis :mock

Emits the source and declares nothing: the mock enters the session only if
you paste it, so it cannot collide with a name you already have. One

holds because nothing was called, and nothing says so.

Nothing is built and nothing is run — this is go/types, like :iface.

go_docis :doc

documentation, or the source   (ri / pry's show-source)

-examples shows the package's runnable examples, each labelled with the
identifier it is an example of. `go doc` does not report them, so they are
read from the sources already on disk — a package whose sources were never
downloaded says so rather than reporting that it has none.

-url prints the pkg.go.dev address at the version the build list has. It
prints and nothing else: no fetch, no browser. When the version cannot be
determined — the standard library, a replaced module, a session with no
requirements — the address is version-independent and says so.

-pkg says the argument names a package, so a name that is also a symbol
resolves to the package or is reported as unresolved, rather than quietly
answering about the other one.

One flag at a time: they are four questions about a name, not four
adjustments to one answer. Output past a screenful is paged, and is still
printed in full through a pipe.

expr reads: [-src | -examples | -url | -pkg] <name>

Flags, written into expr as at the prompt:
  -src  the implementation rather than the documentation
  -examples  the package's runnable examples, read off disk
  -url  the pkg.go.dev address at the version in use
  -pkg  read the name as a package, never as a symbol

Examples (expr):
  "strings.Cut"
  "-src strings.Cut" — the source — pry's show-source
  "-examples strings"
  "-url github.com/google/uuid.New" — an address at the version the build list has; nothing is fetched
  "-pkg errors" — the package, where a symbol could have answered instead

session_resetis :reset

Bare :reset clears the entries and leaves the requirements alone, so a
session cleared to try the same library a different way does not have to
fetch it again.

the plugins that depended on them. A requirement the attached host owns is
left alone: it belongs to the host's go.mod, which gluon never edits.

go_sinceis :since

what each Go release added, from the toolchain you have

With no argument, every release the installed toolchain describes, newest
first. With a version, that release: its language changes, its GODEBUG
entries, and its standard library additions a package at a time.

The additions are read from $GOROOT/api/go1.N.txt and the behaviour changes
from $GOROOT/doc/godebug.md — the release record the distribution already
ships. Nothing is fetched. Every api line since Go 1.19 carries the number
of the proposal that accepted it, so the go.dev/issue link beside a
declaration is a fact on disk rather than a guess.

-lang is the language changes alone, as prose with a runnable snippet. No
api file describes a change to the language, so these are written by hand,
and a release nobody has written up says so rather than reporting that its
syntax did not move.

-pkg <path> is every addition to one import path across every release —
which release added maps.Keys, and what else arrived with it.

-run <name> evaluates a language note's snippet into this session. It is
what the run choice on a note hands back, and it adds to the session and
the scratchpad like any line you typed, so :branch first if that matters.
A note needing a go directive above the one this session builds at is
refused with which of the two numbers is short, rather than left to the
compiler to report against a temp path you never wrote.

expr reads: [-lang | -pkg <path> | -run <name>] [version]

Flags, written into expr as at the prompt:
  -lang  the language changes alone, as prose with a snippet
  -pkg <path>  every addition to one import path, across releases
  -run <name>  evaluate a language note's snippet in this session

Examples (expr):
  "1.23 -lang"
  "-pkg maps" — which release added maps.Keys, and what came with it
  "1.23 -run range-over-func"

This tool runs code by replaying the session; side effects repeat.

go_diffis :diff

Reports only the differences, each with the path to it — .Name, [3],
or . for the value itself. Two structs of a dozen fields that differ in
one produce one row, which is the reason to have this rather than print
both and read them.

comparison there rather than calling every field different, and a
length or a missing key is stated as itself.

Both values come from one evaluation, so a value derived from anything
non-deterministic is compared against the same run it was taken from.
The value printer caps a large collection, and when it did the report
says the comparison covers only the part it could see.

go_benchis :bench

ns/op, B/op and allocs/op, through testing.B

B/op and allocs/op are always reported; there is no -mem flag because
there is nothing for it to turn on. The three flags say how the
benchmark is run, never what is measured. -count exists so a
measurement can be judged for consistency; -cpu is the only way to see
a contention effect from the REPL.

Flags are read only while they lead: everything from the first word
that is not one of them is the expression, verbatim.

Two expressions separated by a top-level comma are benchmarked side by
side with the ratio between them — the comparison you would otherwise
run twice and hold in your head. Both are measured in one evaluation,
so neither is timed against a different replay of the session, and a
comma inside brackets, parentheses, braces or a literal is not the
separator.

expr reads: [-count <n>] [-cpu <list>] [-profile] <exp>[, <other>]

Flags, written into expr as at the prompt:
  -count <n>  run it n times; report min, median and max
  -cpu <list>  once per GOMAXPROCS value, each labelled: 1,2,4
  -profile  keep the run's CPU profile, and say where it went

Examples (expr):
  "strings.Repeat(\"ab\", 64)"
  "-count 5 fmt.Sprint(42), strconv.Itoa(42)" — side by side, with the ratio between them
  "-cpu 1,4 -profile strings.Repeat(\"ab\", 1024)"

This tool runs code by replaying the session; side effects repeat.

go_profileis :profile

where the time went, from a real run

Evaluates the expression once with the CPU profiler running, lists the
functions that accounted for the most time, and names the file the
profile went to and the `go tool pprof` command that opens it.

The sample count is printed every time, and it is the first thing to
read. Go samples at 100 Hz, so an expression that finishes in a
millisecond contributes no samples at all and the ranking under it means
nothing. Below a hundred samples the report says so.

There is no :profile <port>. The child process exits when the evaluation
ends, so there is nothing left to serve a live profile from — this
captures one from a run that really happened instead.

expr reads: <exp>

Examples (expr):
  "sha256.Sum256(make([]byte, 64<<20))" — the functions that took the time, and the pprof command for the rest

go_grpcis :grpc

what a gRPC server exposes, and one unary call against it

With an address alone, lists the services and methods the server exposes,
discovered through server reflection. A method that needs a stream is listed
and marked, because gluon compiles each line into a program that exits and a
stream has nowhere to live — reading one message and hanging up would return
a number that looks like an answer and is not.

With a `pkg.Service/Method` as well, calls it. -d '<json>' is the request and
defaults to {}; it is checked against the reflected descriptor before the call
is made, so a field you got wrong is named here rather than by the server.

Quote anything with a space in it: no shell has been near the line.

A metadata value may name a variable rather than carry one.
-H 'authorization: Bearer $TOKEN' resolves $TOKEN in the child, so the value
reaches neither :src, nor :save, nor ~/.local/state/gluon/history. A value
whose *shape* says it is a credential is refused instead of sent, because by
then the line as typed is already in the history file and masking the display
would not take it back.

Every call dials and hangs up. gRPC assumes a channel that outlives many
calls and this process outlives one, so latency measured here is the cost of
connecting plus the call and is not a measurement of gRPC. Nothing survives
between calls: no channel, no resolved address, no state a server kept.

The response is never cached. The cache is keyed on program text alone, so
the same call would otherwise answer with what it first saw.

There is no :proto. Reading a .proto off disk needs a compiler that
google.golang.org/protobuf does not contain — internal/plugins/rpc's package
comment records what was examined and what it would take.

gluon mcp

gluon answers questions about Go code from go/types, using the same toolchain that builds it — measured, not guessed. Static tools (go_type, go_methods, go_scope, go_layout, go_doc, session_source, session_history, the interface questions go_implements, go_satisfies, go_cast, go_interface, go_embeds, go_generics, and the test doubles go_mock and go_spy) answer in about a millisecond and never run anything.

Every tool takes optional offset and limit, counted in lines of the answer: ask for what your window holds and the reply says which lines it gave and how many there are. Omit both for the whole answer.

This session is standalone: stdlib and whatever go_eval declares.

gluon mcp --eval

gluon answers questions about Go code from go/types, using the same toolchain that builds it — measured, not guessed. Static tools (go_type, go_methods, go_scope, go_layout, go_doc, session_source, session_history, the interface questions go_implements, go_satisfies, go_cast, go_interface, go_embeds, go_generics, and the test doubles go_mock and go_spy) answer in about a millisecond and never run anything.

Every tool takes optional offset and limit, counted in lines of the answer: ask for what your window holds and the reply says which lines it gave and how many there are. Omit both for the whole answer.

This session is standalone: stdlib and whatever go_eval declares.

Evaluation is enabled. go_eval compiles against the real toolchain (~300ms a call); go_bench measures through testing.B and takes seconds, as go_profile, go_memprof and go_trace do. go_diff compares two values from one run, go_test writes the session's judgement down as a Go test, and session_refresh runs the pinned entries once more. go_err_chain, go_escape, go_slice_headers and session_undo evaluate too. The compiler's own verdicts come from go_inline (what was flattened, and why not), go_asm (one declared function's listing) and go_vet (the toolchain's analysers); go_race runs the expression once under the race detector, whose first call on a machine compiles the instrumented standard library and takes seconds. go_since is the odd one here: it reads what each Go release added out of $GOROOT and costs nothing, and is in this tier only because its -run flag evaluates a language note into the session. The session replays wholesale on every evaluating call, so side effects repeat; session_reset starts over.
