:themethe colour themes, and switch between them

:theme [name]
takes wordsalso :themes
namea theme — :theme lists them
gluon> :theme
the picker: the session repaints as the selection moves
gluon> :theme gruvppuccin-mocha
switch, and write it into config.toml

With a name, switches to it and writes [theme] name into config.toml, so the next session starts in it too.

With none, opens the picker: moving the selection repaints the session underneath it, because the only useful preview of a palette is your own code in it. Enter keeps the highlighted theme, esc puts back the one you started in.

Per-role overrides in config.toml still apply on top of whichever theme is chosen. gluon theme import is how an editor theme becomes one of these.

:settingsevery setting gluon has, and change one

:settings [key [value | -]]
takes wordsalso :set
keya setting — :settings lists them
valuewhat to set it to, or - for its default; key=value works too
gluon> :settings
every setting, its value, and where the value came from
gluon> :settings value.form
one setting explained
gluon> :settings timeout 2m
written into config.toml as one line
gluon> :settings timeout -
back to its default

With nothing, lists them: what each does, what it is now, what it would be otherwise, what it accepts, and whether the value came from config.toml or from a default.

With a key, explains that one. With a key and a value, writes it into config.toml — one line, leaving every other byte alone, so the comments you put there survive. :settings <key> - puts it back to its default.

Both spellings work: :settings timeout 2m and :settings timeout=2m.

A few settings are listed and not settable — an array is not one line, and rewriting one wholesale would take the comments inside it. Those say so.

:settings value.form is the one that changes what you see: table is the bordered box, and tree, columns, line and literal are the other four shapes a value can take. It changes what a terminal draws and nothing else — a pipe, gluon -e and the -json envelopes never see a form.

:tthe type of an expression (Ruby's .class)

:t [-v | -d] <exp>
takes a Go expressionMCP · go_type · static, served without --evalalso :type
-vadd the underlying type and its kind
-drun it once for the dynamic type inside an interface
gluon> :t strconv.Atoi("12")
two values: (int, error)
gluon> :t -v time.Second
the named type, what it is underneath, and its kind
gluon> :t -d r
what is inside the interface r — this one costs a build

Answers from go/types in gluon's own process, so it never builds and comes back in about a millisecond.

-d is the exception: it reports the dynamic type — what is actually inside an interface value — which nothing but a run can know. It costs a build and an execution, and it runs your expression, so a call with a side effect has it. Only at the prompt: the MCP tool stays static and ignores the flag.

:mocka mock implementation of an interface

:mock <type>
takes a Go nameMCP · go_mock · static, served without --eval
gluon> :mock io.ReadCloser
a struct with a func field per method, to paste in

Emits the source and declares nothing: the mock enters the session only if you paste it, so it cannot collide with a name you already have. One settable func field per method, and methods that dispatch to them — including the ones an embedded interface promotes, because the method set is the one :m computes.

A method whose field is unset panics naming itself. Returning zero values instead is how a mock makes a test pass for the wrong reason: the assertion holds because nothing was called, and nothing says so.

Nothing is built and nothing is run — this is go/types, like :iface.

:docdocumentation, or the source (ri / pry's show-source)

:doc [-src | -examples | -url | -pkg] <name>
takes a Go nameMCP · go_doc · static, served without --evalalso :d
namea package, a symbol or a method, as go doc reads it
-srcthe implementation rather than the documentation
-examplesthe package's runnable examples, read off disk
-urlthe pkg.go.dev address at the version in use
-pkgread the name as a package, never as a symbol
gluon> :doc strings.Cut
gluon> :doc -src strings.Cut
the source — pry's show-source
gluon> :doc -examples strings
gluon> :doc -url github.com/google/uuid.New
an address at the version the build list has; nothing is fetched
gluon> :doc -pkg errors
the package, where a symbol could have answered instead

-examples shows the package's runnable examples, each labelled with the identifier it is an example of. go doc does not report them, so they are read from the sources already on disk — a package whose sources were never downloaded says so rather than reporting that it has none.

-url prints the pkg.go.dev address at the version the build list has. It prints and nothing else: no fetch, no browser. When the version cannot be determined — the standard library, a replaced module, a session with no requirements — the address is version-independent and says so.

-pkg says the argument names a package, so a name that is also a symbol resolves to the package or is reported as unresolved, rather than quietly answering about the other one.

One flag at a time: they are four questions about a name, not four adjustments to one answer. Output past a screenful is paged, and is still printed in full through a pipe.

See also :since · :t

Worked through in Inspecting

:sincewhat each Go release added, from the toolchain you have

:since [-lang | -pkg <path> | -run <name>] [version]
takes wordsMCP · go_since · with --eval
versiona Go release — :since lists them
-langthe language changes alone, as prose with a snippet
-pkg <path>every addition to one import path, across releases
-run <name>evaluate a language note's snippet in this session
gluon> :since
every release the installed toolchain describes
gluon> :since 1.23 -lang
gluon> :since -pkg maps
which release added maps.Keys, and what came with it
gluon> :since 1.23 -run range-over-func

With no argument, every release the installed toolchain describes, newest first. With a version, that release: its language changes, its GODEBUG entries, and its standard library additions a package at a time.

The additions are read from $GOROOT/api/go1.N.txt and the behaviour changes from $GOROOT/doc/godebug.md — the release record the distribution already ships. Nothing is fetched. Every api line since Go 1.19 carries the number of the proposal that accepted it, so the go.dev/issue link beside a declaration is a fact on disk rather than a guess.

-lang is the language changes alone, as prose with a runnable snippet. No api file describes a change to the language, so these are written by hand, and a release nobody has written up says so rather than reporting that its syntax did not move.

-pkg <path> is every addition to one import path across every release — which release added maps.Keys, and what else arrived with it.

-run <name> evaluates a language note's snippet into this session. It is what the run choice on a note hands back, and it adds to the session and the scratchpad like any line you typed, so :branch first if that matters. A note needing a go directive above the one this session builds at is refused with which of the two numbers is short, rather than left to the compiler to report against a temp path you never wrote.

Worked through in Inspecting

:diffwhat differs between two values, and where

:diff <a>, <b>
takes a Go expressionMCP · go_diff · with --eval
gluon> :diff got, want
only what differs, each with the path to it

Reports only the differences, each with the path to it — .Name, [3], or . for the value itself. Two structs of a dozen fields that differ in one produce one row, which is the reason to have this rather than print both and read them.

A difference in shape is reported as one: different types stop the comparison there rather than calling every field different, and a length or a missing key is stated as itself.

Both values come from one evaluation, so a value derived from anything non-deterministic is compared against the same run it was taken from. The value printer caps a large collection, and when it did the report says the comparison covers only the part it could see.

:benchns/op, B/op and allocs/op, through testing.B

:bench [-count <n>] [-cpu <list>] [-profile] <exp>[, <other>]
takes a Go expressionMCP · go_bench · with --eval
othera second expression, measured beside the first
-count <n>run it n times; report min, median and max
-cpu <list>once per GOMAXPROCS value, each labelled: 1,2,4
-profilekeep the run's CPU profile, and say where it went
gluon> :bench strings.Repeat("ab", 64)
gluon> :bench -count 5 fmt.Sprint(42), strconv.Itoa(42)
side by side, with the ratio between them
gluon> :bench -cpu 1,4 -profile strings.Repeat("ab", 1024)

B/op and allocs/op are always reported; there is no -mem flag because there is nothing for it to turn on. The three flags say how the benchmark is run, never what is measured. -count exists so a measurement can be judged for consistency; -cpu is the only way to see a contention effect from the REPL.

Flags are read only while they lead: everything from the first word that is not one of them is the expression, verbatim.

Two expressions separated by a top-level comma are benchmarked side by side with the ratio between them — the comparison you would otherwise run twice and hold in your head. Both are measured in one evaluation, so neither is timed against a different replay of the session, and a comma inside brackets, parentheses, braces or a literal is not the separator.

See also :profile · :memprof · :esc

Worked through in Measuring

:profilewhere the time went, from a real run

:profile <exp>
takes a Go expressionMCP · go_profile · with --eval
gluon> :profile sha256.Sum256(make([]byte, 64<<20))
the functions that took the time, and the pprof command for the rest

Evaluates the expression once with the CPU profiler running, lists the functions that accounted for the most time, and names the file the profile went to and the go tool pprof command that opens it.

The sample count is printed every time, and it is the first thing to read. Go samples at 100 Hz, so an expression that finishes in a millisecond contributes no samples at all and the ranking under it means nothing. Below a hundred samples the report says so.

There is no :profile <port>. The child process exits when the evaluation ends, so there is nothing left to serve a live profile from — this captures one from a run that really happened instead.

See also :memprof · :bench

:memprofwhere the allocations went, from a real run

:memprof <exp>
takes a Go expressionMCP · go_memprof · with --eval
gluon> :memprof strings.Repeat("x", 1<<20)
the sites that allocated the most bytes

The same capture as :profile against the heap profiler: the sites that accounted for the most allocation, and the file that holds the rest.

:tracethe call stack the expression is evaluated on

:trace <exp>
takes a Go expressionMCP · go_trace · with --eval
gluon> :trace fib(10)
the stack it runs on, each frame named by the entry it came from

Captures the stack where the expression is evaluated and names each frame by the session entry it came from, not the temp file the program was generated into.

It holds the expression's callers, not its callees: a function it is about to call has not been entered yet, and by the time that call returns its frame is gone. gluon compiles each line into a program that exits, so there is no process to pause and no in-REPL breakpoint to set. For what happens underneath a call, :save -debug is the way out.

Worked through in Measuring

:inlinewhat the compiler decided about inlining

:inline <exp|func>
takes a Go expressionMCP · go_inline · with --eval
exp|funca line whose calls to report, or a function this session declared
gluon> :inline add(1, 2)
every call on the line, and whether it was flattened
gluon> :inline big
whether a function you declared can be inlined, and its cost

With an expression, reports every call on that line the compiler did or did not flatten. With the name of a function this session declared, reports whether it can be inlined at all, what it costs, and — when it cannot — the compiler's own reason, which is usually a cost against a budget.

It builds and never runs, exactly as :esc does: inlining is decided at compile time, so there is nothing an execution could add. The two commands are the same build asked for a different half of its output.

The wording is the compiler's, not a paraphrase of it. A decision about a function declared on an earlier line is answered by naming that function, not by asking about a line that happens to call it.

See also :esc · :asm

Worked through in Measuring

:asmthe assembly emitted for one declared function

:asm <func>
takes a Go nameMCP · go_asm · with --eval
funca function or method this session declared: F, T.M or (*T).M
gluon> :asm add
gluon> :asm (*Stack).Push

Shows the listing for one function or method this session declared, and nothing else. A method is named T.M or (*T).M; either spelling finds it, because which one is right is the receiver's business rather than yours.

Every position in the listing names the entry and line it came from, so no path under the temp directory appears. Long listings open in a pane; the same bytes are always in the linear output too.

Only the session's own functions. The listing flag applies to the package named on the command line, deliberately — widening it to the standard library would recompile it under different flags and throw away the warm build cache every line in this REPL depends on. So :asm strings.Index is refused rather than answered slowly.

A function inlined at every call site is dropped by the linker and has no listing of its own. That is reported as what it is.

:vetwhat go vet says about the session

:vet [exp]
takes a Go expressionMCP · go_vet · with --eval
gluon> :vet
the session, each finding against the entry it belongs to
gluon> :vet fmt.Printf("%d", "x")
the session with this line appended

Runs the toolchain's own analysers over the session — with the expression appended when you give one — and reports each finding against the entry and line it belongs to. Nothing is built and nothing is run: vet type-checks the package itself, which is why it costs about half a second rather than a build.

Findings in the code gluon generates around your lines are never shown. One there would be gluon's bug, and there is nothing you could do about it.

It vets the session, not the host. go vet . names the main package, and an attached host's packages are compiled into it rather than analysed — their findings belong to that project's own go vet ./....

There is no :lint. staticcheck and its neighbours are dependencies gluon does not have; vet is the analyser the toolchain already ships.

See also :race

Worked through in Measuring

:racerun it once under the race detector

:race <exp>
takes a Go expressionMCP · go_race · with --eval
gluon> :race incrementTwice()
any race in that run, each frame named by its entry

Builds the session with -race, evaluates the expression once, and names every frame of any data race by the entry it came from. The expression's own value is printed either way: a race is something that happened during the run, not instead of it.

Finding nothing is not proof of anything, and the output says so every time. The detector observes one interleaving of one run; a race that needs a different schedule is still there.

The first :race on a machine compiles the race-instrumented standard library, which takes several seconds. Later ones reuse it and cost about what an ordinary line does. The instrumented binary is built beside the ordinary one and goes with the session directory.

On a platform the detector does not support, the toolchain's own message is shown and nothing is retried without the flag — a value from a run nothing was watching, under a command called :race, would be worse than no answer.

See also :vet · :trace

Worked through in Measuring

:envthe process environment, redacted (Rails.env's neighbour)

:env [pattern]
takes words
patternpart of a variable's name, any case
gluon> :env
gluon> :env database
the variables whose name contains it, secrets masked

Sorted by name, and filtered to the names containing pattern. Nothing is built and nothing is run — this is gluon's own environment, which is what every line it evaluates inherits.

A value is hidden when its shape says it carries a secret: a connection string, a bearer token, a vendor-prefixed key. The name of the variable is never consulted and never hidden — a NOTE holding a DSN is redacted and a PASSWORD_HINT holding "ask the team" is not.

Shape is not a guarantee. A secret in a format gluon does not recognise is shown; a value hidden that was not one is recoverable, because the name beside it always is. There is no way to set a variable from here: it would change every later line while leaving no trace in :src.

See also :conf · :db

:confread a project config file, redacted

:conf [file]
takes words
filea TOML, YAML or JSON file
gluon> :conf
the config files the project search found, and where it looked
gluon> :conf config/app.yaml
its keys, dotted, secrets masked

With a file, reads TOML, YAML or JSON and lists its keys in dotted form — database.primary.url — with the same shape-based redaction :env uses. A file that does not parse shows no keys at all: a configuration displayed as half read hides exactly the part that is missing.

With no file, lists what the project search found and where it looked, so that "found nothing" and "did not look" are different answers. It is the same bounded search :db runs, ceilinged at the repository root, and the same cached result — paid for once per :use rather than per line.

It only reads a project's config. gluon init writes a project one, and :settings changes gluon's own.

:inspectbrowse a large value in a view that scrolls

:inspect [-n <k>] <e>
takes a Go expressionalso :i
-n <k>describe k elements, for this one view
gluon> :inspect rows
a view that scrolls; one line is left behind
gluon> :inspect -n 5000 rows

Opens the one thing a printed table cannot be. It takes the whole screen, prints nothing while it is up, and leaves one line in scrollback on close. Through a pipe it prints the ordinary rendering instead, so nothing is lost.

-n k describes k elements of the collection for this one invocation, so a long slice can be browsed whole without the session's value.items moving. It is the item bound only: depth is not what a table of rows shows, and the budget on the whole value still applies, so a collection of large elements may stop short of k.

Worked through in Rendering

:httpissue a request, and render what came back

:http <method> <url> [-H <header>]... [-d <body>] [-t <duration>]
takes words
methodGET HEAD POST PUT PATCH DELETE OPTIONS TRACE, any case
urlhttp:// or https://, written out whole
-H <header>a header, written 'Name: value'; repeat it for another
-d <body>the request body
-t <duration>how long to wait: 5s, 500ms, 1m (30s by default)
gluon> :http GET https://api.github.com/zen
gluon> :http POST https://httpbin.org/post -d '{"a": 1}' -t 5s
gluon> :http GET https://api.github.com/user -H 'Authorization: Bearer $GH_TOKEN'
the token is named, so its value reaches no history file

Quote anything with a space in it: no shell has been near the line.

A header value may name a variable rather than carry one. -H 'Authorization: Bearer $TOKEN' resolves $TOKEN in the child, so the value reaches neither :src, nor :save, nor ~/.local/state/gluon/history. A value whose shape says it is a credential is refused instead of sent, because by then the line as typed is already in the history file and masking the display would not take it back. That is the whole of what this protects: a token written into an http.Get you typed yourself is not something gluon can catch.

The body is read to 64 KiB and the notice says what was skipped. A non-textual content type is summarised — its type and size — rather than printed.

Nothing survives between requests: no cookie jar, no reused connection, no client. The child process dies after every line, so there is nowhere to keep one, and a command implying otherwise would teach a lie.

The response is never cached. The cache is keyed on program text alone, so the same request would otherwise answer with what it first saw.

:grpcwhat a gRPC server exposes, and one unary call against it

:grpc <addr> [method] [-H <header>]... [-d <json>] [-t <duration>] [-tls]
takes wordsMCP · go_grpc · with --eval, while the plugin is activegrpc plugin
addrhost:port; a name-resolver scheme passes through as written
methodpkg.Service/Method, as the listing prints it
-H <header>call metadata, written 'name: value'; repeat it for more
-d <json>the request, checked against the descriptor ({} by default)
-t <duration>how long to wait: 5s, 500ms, 1m (30s by default)
-tlsdial with TLS instead of plaintext
gluon> :grpc localhost:50051
what the server exposes, discovered through reflection
gluon> :grpc localhost:50051 shop.v1.Orders/Get -d '{"id": 42}' -t 5s
gluon> :grpc api.internal:443 shop.v1.Orders/Get -tls -H 'authorization: Bearer $TOKEN'
the token is named, so its value reaches no history file

With an address alone, lists the services and methods the server exposes, discovered through server reflection. A method that needs a stream is listed and marked, because gluon compiles each line into a program that exits and a stream has nowhere to live — reading one message and hanging up would return a number that looks like an answer and is not.

With a pkg.Service/Method as well, calls it. -d '<json>' is the request and defaults to {}; it is checked against the reflected descriptor before the call is made, so a field you got wrong is named here rather than by the server.

Quote anything with a space in it: no shell has been near the line.

A metadata value may name a variable rather than carry one. -H 'authorization: Bearer $TOKEN' resolves $TOKEN in the child, so the value reaches neither :src, nor :save, nor ~/.local/state/gluon/history. A value whose shape says it is a credential is refused instead of sent, because by then the line as typed is already in the history file and masking the display would not take it back.

Every call dials and hangs up. gRPC assumes a channel that outlives many calls and this process outlives one, so latency measured here is the cost of connecting plus the call and is not a measurement of gRPC. Nothing survives between calls: no channel, no resolved address, no state a server kept.

The response is never cached. The cache is keyed on program text alone, so the same call would otherwise answer with what it first saw.

There is no :proto. Reading a .proto off disk needs a compiler that google.golang.org/protobuf does not contain — internal/plugins/rpc's package comment records what was examined and what it would take.

See also :http · :pb
