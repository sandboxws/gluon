gluon

A REPL and scratch runner for Go
gluon [flags]
gluon is a REPL and scratch runner for Go, for when you want to check what
s[i] prints without writing a main package first.

It compiles with your real Go toolchain, so the semantics are the compiler's:
every line re-renders the session into a genuine Go program and builds it.
-e, -eval <stringArray>evaluate a line of Go and print the result (repeatable)
-host <string>attach the session to the Go module at this directory (use . for the working directory)
-jsonwith -e, print one JSON object instead of the plain rendering
-no-scratchdo not open a scratchpad, so nothing about this session is written down
-scratch <string>open this scratchpad instead of the configured one (interactive sessions only)
Shellexamples
# start the REPL
gluon
# evaluate and print, the ruby -e shape
gluon -e 'strings.ToUpper("hi")'
# the same engine, no banner
echo 'x := 1' | gluon
# attach to the module you are standing in
gluon -host .

gluon completion bash

Generate the autocompletion script for bash
gluon completion bash
Generate the autocompletion script for the bash shell.

This script depends on the 'bash-completion' package.
If it is not installed already, you can install it via your OS's package manager.

To load completions in your current shell session:

	source <(gluon completion bash)

To load completions for every new session, execute once:

#### Linux:

	gluon completion bash > /etc/bash_completion.d/gluon

#### macOS:

	gluon completion bash > $(brew --prefix)/etc/bash_completion.d/gluon

You will need to start a new shell for this setup to take effect.
-no-descriptionsdisable completion descriptions

gluon doctor

Report what gluon detects here
gluon doctor [dir] [flags]
Report what gluon can see from this directory: the Go toolchain it will use,
the config it read, the module it would attach to, and every package that
module leaves importable from a session.

On darwin it also times a freshly linked binary, because Gatekeeper
assessment is ~105ms of every line that has to run and `spctl --status`
cannot tell you whether this terminal is exempt.
-jsonprint one JSON object instead of a report
Shellexamples
# what gluon sees here
gluon doctor
# what it would see from another project
gluon doctor ~/src/shop
# is this terminal exempt from Gatekeeper assessment?
gluon doctor -json | jq .gatekeeper
$

gluon init

Record where this project's database is
gluon init [dir] [flags]
Detect the database a project uses, and write down where it is so :db and
:query can find it again.

gluon never stores a password. What it records is the name of the environment
variable, or the file and key, that a connection string lives in — so the
config it writes is safe to read, to share, and to commit.

Nothing is written without being asked: -no-prompt prints the block it would
have written and stops there.
-forceappend even when an entry of this name exists
-globalwrite to ~/.config/gluon/config.toml
-jsonprint one JSON object instead of a report
-localwrite to ./gluon.toml, which travels with the project
-no-promptprint what would be written and stop
-writewrite without asking (needs -local or -global)
Shellexamples
# look, ask, and write
gluon init
# what would it write?
gluon init -no-prompt
# write it without asking, to the global config
gluon init -no-prompt -write -global
# what did it detect?
gluon init -json | jq .detected

gluon mcp

serve the session's inspectors to a coding agent (MCP over stdio)
gluon mcp [flags]
gluon mcp speaks the Model Context Protocol over stdio. The inspecting
commands become tools: go_type, go_methods, go_scope, go_layout, go_doc, and
the interface questions — go_implements, go_satisfies, go_cast, go_interface,
go_embeds, go_generics — answered from go/types in about a millisecond, by the
same toolchain that builds your code.

When the working directory is inside a Go module, the session attaches to
it — internal/ packages included — because installing the server in a
project's MCP config is the asking. -host picks a different module; -host
off serves a standalone session.

Tools that run code (go_eval, go_bench, plugin tools, session_reset) are
exposed only with --eval. Evaluation replays the whole session each call,
so side effects repeat — the tool descriptions say so, to the one reader
who never skims.
-evalalso expose the tools that run code: go_eval, go_bench, the profilers, go_diff, go_test, plugin tools, session_reset
-host <string>module to attach to (default: the module containing the working directory; off: none)
Shellexamples
# .mcp.json
{"mcpServers": {"gluon": {"command": "gluon", "args": ["mcp"]}}}
# with evaluation enabled
{"mcpServers": {"gluon": {"command": "gluon", "args": ["mcp", "--eval"]}}}

gluon new

Scaffold a scratch program and open it
gluon new [topic] [flags]
Write a self-contained scratch module and open it in your editor.

One directory per scratch, each with its own go.mod, so gopls stays fully
alive in the file — completion, hover, jump-to-definition. A single
//go:build ignore file works too, but gopls greys it out entirely, so that
form is -flat and not the default.
-debugwrite a debugger launch configuration beside the module (not with -flat)
-flatwrite one //go:build ignore file instead of a module directory (no gopls)
-host <string>nest the scratch under the module at this directory, so it can import its packages
-no-editcreate it but do not open an editor
-no-prompt <gluon new>do not ask for a topic; use the default as gluon new always has
-runrun it after the editor exits
Shellexamples
# an untitled scratch
gluon new
# named, so the directory says what it is
gluon new heap-sort
# one that can import the surrounding project
gluon new probe -host .
# a single //go:build ignore file (no gopls)
gluon new x -flat
# one a debugger can open, configuration included
gluon new parser-bug -debug
$

gluon run

Run a scratch
gluon run [path] [-- args...] [flags]
Run a scratch program — the most recent one by default, or the directory
or flat file named. Arguments after -- go to the program, not to gluon.
-listlist the scratches, newest first
Shellexamples
# the most recent scratch
gluon run
# a named one, directory or flat file
gluon run ~/scratch/2026-08-28-heap-sort
# what there is to run
gluon run -list

gluon scratch

List the scratchpads, or show and remove one
gluon scratch
A scratchpad is a named session on disk: the lines you typed, what is
pinned, and the module and host it takes to replay them. The REPL lands in
one and writes every line into it.

`gluon scratch show` prints what one holds without evaluating any of it,
which is the way to read a scratchpad you are not sure you want to run.
Shellexamples
# what there is
gluon scratch
# read one without running it
gluon scratch show parser-bug
# start a REPL in one
gluon -scratch parser-bug
$

gluon scratch rm

Remove a scratchpad
gluon scratch rm <name> [flags]
Shows what the scratchpad holds and asks before removing it. Without a
terminal to ask on, -force is required.
-forceremove it without asking
$

gluon scratch show

Print what a scratchpad holds, without running it
gluon scratch show <name>
Prints the entries a scratchpad holds, in the order they were typed, and
evaluates none of them. Reopening a scratchpad replays it — an entry that
wrote a file writes it again unless it is pinned — so this is the
read-before-you-run path.
$

gluon theme

list gluon's colour themes, and import one from an editor
gluon theme
Themes live in ~/.config/gluon/themes as TOML, one colour per role.
gluon ships twenty-three: `go`, the default, and `go-light`, the same
palette for a white terminal; `terminal`, which is your own sixteen
ANSI colours — what gluon looked like before it had a palette of its
own; the five dark Gruvppuccin palettes; and fifteen converted from the
editor themes of the same names, six of them light.

gluon paints no background, because your terminal owns that — so a
theme says which ground it was drawn for and the list prints it.

Select one in ~/.config/gluon/config.toml:

    [theme]
    name = "terminal"

Individual roles still override whatever the theme said, so a theme you
almost like costs one line rather than a copy.
Shellexamples
# what is installed, and what is on
gluon theme
# the colours a theme actually resolves to
gluon theme show terminal
# turn an editor theme into one of gluon's
gluon theme import ~/Downloads/Monokai.tmTheme
$

gluon theme import

convert a TextMate .tmTheme or VS Code theme into a gluon theme
gluon theme import <file> [flags]
TextMate and VS Code describe the same thing — scopes and the colours
they take — so both are read the same way and mapped onto gluon's roles.
An IntelliJ scheme names attributes instead, and colours a whole editor
rather than a language, so it decides three roles the other two cannot:
its caret becomes the prompt and its line numbers become the furniture.

The mapping is lossy in one direction and cannot be otherwise: about a
third of gluon's palette describes a terminal program rather than a
syntax highlighter, and no scope in any editor theme means "the
reverse-i-search prompt". Those keep gluon's own values, and the report
says which — so every guess is on screen, in a file you can edit.
-forceoverwrite a theme of the same name
-name <string>the theme's name (default: the file's, slugified)
-printwrite to stdout instead of the themes directory
$

gluon theme show

the colours a theme resolves to, one role per line
gluon theme show [name]
Every role, its value, and a swatch drawn in it — which is also the way
to see what a hex colour becomes on a terminal that has fewer than
sixteen million of them.

With no name, the theme your config selects, including any per-role
overrides it sets.
$
