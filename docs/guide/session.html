The program your session became

A session is a list of entries — the lines you typed — and every line renders all of them into one Go program, builds it and runs it. :src shows that program, exactly as the compiler saw it.

gluon> x := []int{3, 1, 2}
gluon> slices.Sort(x)
gluon> x
([]int) len=3 cap=3
╭───┬───────╮
│ # │ value │
├───┼───────┤
│ 0 │ 1 │
│ 1 │ 2 │
│ 2 │ 3 │
╰───┴───────╯
gluon> it[0]
(int) 1
gluon> :src
package main
import (
"slices"
)
func main() {
x := []int{3, 1, 2}
_ = x
slices.Sort(x)
_1 := x
__gluonPrint(_1)
__gluonPrint(_1[0])
}

Everything gluon does to your lines is there to read: the import it added, the _ = x that keeps Go from calling x unused, it rewritten to the _1 it meant, and the call that prints the last value. Nothing is hidden, so when a line does something you did not expect, the program it ran is one command away. A long program opens in a view at the prompt and prints whole through a pipe.

2

Every line replays — and what that costs

the honest limitation

Because every line re-runs the whole session, side effects repeat: a request fires again, a file is written again, time.Now() moves on and rand changes its mind. Output from the replayed lines is muted, so you only see the newest line's — but the re-execution is real.

gluona line with an effect, and :pin
gluon> hit := func() { f, _ := os.OpenFile("hits", os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0o644); f.WriteString("x"); f.Close() }
gluon> hit()
gluon> b, _ := os.ReadFile("hits")
gluon> len(b)
(int) 3
gluon> len(b)
(int) 4
gluon> :hist
1 hit := func() { f, _ := os.OpenFile("hits", os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0o644); f.WriteString("x"); f.Close() }
2 hit()
3 b, _ := os.ReadFile("hits")
4 len(b) _1
5 len(b) _2
gluon> :pin 2
pinned 2 — it will not run again
gluon> len(b)
(int) 4
gluon> len(b)
(int) 4
gluon> :pin
2 hit()
gluon> :refresh
refreshed — 1 pinned entry ran again
(int) 5
gluon> len(b)
(int) 5
gluon> :unpin 2
unpinned 2 — it runs again from here
gluon> len(b)
(int) 7

Each len(b) is one larger than the last, because each line ran hit() again. :pin is the defence: it takes an entry out of the program — you are saying it has already happened — so replay stops running it. :pin on its own lists what is pinned, and :hist marks it.

A pin is refused when a later entry uses what the pinned one bound, and says which entry that is. gluon does not invent the missing value: the printer writes a display form, not a literal — a uint8 reads 195 (0xc3) — so rebuilding a value from what was printed would be a guess, and a guess here is a wrong answer that looks like a right one.

:refresh runs the program once with every pin lifted and puts the pins back — for when the code under a pinned entry changed and the result it holds is stale. :unpin puts an entry back for good: unpinning replays the session, and so does every line after it, which is why the count moved by two.

3

Editing the entries

:hist numbers the entries, :drop removes one by its number, :undo removes the last, and :reset removes them all.

gluon> a := 1
gluon> b := 2
gluon> c := a + b
gluon> c
(int) 3
gluon> :hist
1 a := 1
2 b := 2
3 c := a + b
4 c _1
gluon> :drop 2
error: undefined: b
c := a + b
^ — entry kept
gluon> :undo
undone (3 entries left)
gluon> :hist
1 a := 1
2 b := 2
3 c := a + b
gluon> :reset
session cleared
gluon> :hist
nothing in the session yet

A removal that would leave the session unable to build is put back, with the reason: c reads b, so b stays. :drop is also refused when a later line reads it, or an _N the removal would renumber, because that line would silently start meaning something else.

:reset clears the entries and keeps the modules you added, so trying the same library a different way does not fetch it again; :reset -deps clears both. u in vim mode, by the way, undoes typing, not entries: the two share a name and nothing else. Editing has the keys, and :edit, which edits every entry at once.

4

Snapshots

:bookmark records the session under a name and takes nothing away from it. :restore puts one back and replays it. :branch is a bookmark for when you had not decided to take one.

gluon> x := 10
gluon> :bookmark before
before: 1 entry, for this session
gluon> x = x * 2
gluon> x
(int) 20
gluon> :branch
b2: 3 entries, for this session
the session is unchanged; :restore b2 comes back here
gluon> x = 99
gluon> x
(int) 99
gluon> :restore before
restored before (1 entry)
gluon> x
(int) 10
gluon> :bookmark
snapshots, for this session only:
before 1 entry
b2 3 entries
:restore <name> goes back to one; :scratch keeps a session past this process

:branch with no name makes one up and prints it, because having to invent a name is the thing it exists to remove — the state before an experiment is recoverable without having thought of it first. A snapshot holds the entries, their order and what is pinned.

A restore that fails to replay puts back the session you were leaving and says so: a restore that could destroy the state it was moving away from would be worse than none. Snapshots last for this session and never reach the disk. Scratchpads are what make a session durable.

5

Yesterday's lines

ctrl-r walks the history file a line at a time and :hist numbers the session; neither gets you the expression you had right in yesterday's session. :replay searches the whole file and brings the matches in.

gluon> :replay repeatopens a view
1 history line matching "repeat", oldest first:
1 s := strings.Repeat("ab", 3)
enter brings them in; nothing has run yet
gluon> :replay -run repeat
brought in 1 line from history
gluon> s
(string) "ababab" len=6

The matches are shown before any of them runs. A history line is a line somebody typed, some of them wrote something, and the session replays every entry on every later line — so what is about to happen is printed verbatim rather than counted. enter in the view brings them in, q leaves without running anything, and :replay -run is the form to type when you already know what the pattern matches — and the form a pipe has. Meta commands are skipped: replaying a :reset would clear the session it was being replayed into.

From a file, and into a test

:load reads a file in, a construct at a time, as though each were typed. :test goes the other way: it writes the expression you just checked, and the value you judged right, down as a Go test.

gluon> :load snippets.go
loaded snippets.go
gluon> price.String()
(string) "$12.50" len=6
gluon> :test price.String()
// TestPriceString was generated by gluon from a value observed at the prompt.
// It records what price.String() produced, not what it should produce: the
// judgement that the answer was right was made at the prompt, and this only
// writes it down.
func TestPriceString(t *testing.T) {
// The session bound these at the prompt, where they are locals inside
// main(). The test carries them so the expression can be evaluated again.
price := Money(1250)
want := "$12.50"
got := price.String()
if got != want {
t.Errorf("price.String() = %v, want %v", got, want)
}
}
— 1 test held; :save -test writes it beside the program
gluon> :test -table strings.Fields(" a b ")
// TestStringsFieldsAB was generated by gluon from a value observed at the prompt.
// It records what strings.Fields(" a b ") produced, not what it should produce: the
// judgement that the answer was right was made at the prompt, and this only
// writes it down.
func TestStringsFieldsAB(t *testing.T) {
tests := []struct {
name string
got []string
want []string
}{
{"strings.Fields(\" a b \")", strings.Fields(" a b "), []string{"a", "b"}},
}
for _, tc := range tests {
t.Run(tc.name, func(t *testing.T) {
// The value's type is not comparable with ==, so this asserts deep equality.
if !reflect.DeepEqual(tc.got, tc.want) {
t.Errorf("%s = %v, want %v", tc.name, tc.got, tc.want)
}
})
}
}
— 2 tests held; :save -test writes them beside the program

:load stops at the first construct that fails, and leaves out an unfinished one at the end rather than reporting against text that may still be being written. The file is read once; :load it again after changing it.

You tried an expression, looked at the answer and decided it was right. That is got, want and a judgement — the whole content of a Go test — and gluon already holds the expression, its type and its value, so :test writes it, carrying the locals the expression needs. The doc comment says the expectation is what was observed, not what is correct; that judgement stays yours, which is why it prints rather than writes. :test -table shapes it so a second case can join, :save -test keeps what was generated, and a value with no literal form — a pointer, a channel, a func — is refused with the part that caused it rather than emitted as a test that does not compile.

7

Goroutines

A go statement on its own would print nothing: main returns before the goroutine is ever scheduled. So gluon waits briefly for the goroutines your lines started — and says that it did, because a real main would not have.

gluon> go func() { fmt.Println("from a goroutine") }()
from a goroutine
[gluon waited 137µs for 1 goroutine(s) — a real main would have exited here]

The wait is bounded at two seconds, and a goroutine still running at the deadline is reported rather than waited on for ever. It covers the goroutines the session's own code started: a library keeps goroutines of its own for as long as the value that owns them — database/sql one per open *sql.DB — and those are left alone, as a real main would leave them. When nothing was started, nothing is said.
