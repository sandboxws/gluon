1

How fast

testing.B

:bench runs an expression through a real testing.B — the numbers go test -bench would give for the same expression, without the test file.

gluonone expression, five runs, two side by side, two CPU counts
gluon> :bench strings.Repeat("ab", 100)
13,966,912 iterations
82 ns/op 208 B/op 1 allocs/op
gluon> :bench -count 5 strings.Repeat("ab", 100)
5 runs min median max
ns/op 79 80 82
B/op 208 208 208
allocs/op 1 1 1
iterations 14,696,539 15,007,393 15,442,566
gluon> n := 42
gluon> :bench strconv.Itoa(n), fmt.Sprint(n)
a strconv.Itoa(n)
b fmt.Sprint(n)
a b b/a
ns/op 2 38 19.00x
B/op 0 2 n/a
allocs/op 0 1 n/a
gluon> :bench -cpu 1,4 strings.Repeat("ab", 1024)
GOMAXPROCS=1
5,025,478 iterations
251 ns/op 2048 B/op 1 allocs/op
GOMAXPROCS=4
4,350,894 iterations
254 ns/op 2048 B/op 1 allocs/op
gluon> :bench -profile strings.Repeat("ab", 100)
13,522,123 iterations
85 ns/op 208 B/op 1 allocs/op
cpu profile $TMPDIR/gluon-session-3419275239/bench-1790205306697740000.pprof
go tool pprof $TMPDIR/gluon-session-3419275239/bench-1790205306697740000.pprof

B/op and allocs/op are always reported; there is no -mem flag, because there would be nothing for it to turn on. The flags say how the benchmark is run, never what is measured, and they are read only while they lead — everything from the first word that is not one of them is the expression, verbatim.

:bench -count runs it more than once and reports the spread, which is what lets a number be trusted or distrusted. It gives the minimum, median and maximum rather than a standard deviation: at five runs a deviation is computed from too few samples to mean what a reader assumes, and these three numbers were all actually seen.

Two expressions separated by a comma are measured side by side, with the ratio between them — the comparison you would otherwise run twice and hold in your head. Both run in one evaluation, so neither is timed against a different replay of the session, and a comma inside brackets, braces or a literal is not the separator. A quantity that is zero on the left has no ratio, and says so rather than printing an infinity.

:bench -cpu runs once per GOMAXPROCS value and labels each, the one way to see a contention effect from a prompt. :bench -profile keeps the run's CPU profile and prints the command that opens it. It goes into the session's own temp directory: gluon never writes into your project.

2

Where the time went

pprof

:bench says how much. :profile says where: it runs the expression once with the CPU profiler on and ranks the functions that took the time, naming the session entry and the line each came from. :memprof does the same against the heap.

gluona CPU profile and a heap profile, from real runs
gluon> func hot(n int) int {
...> total := 0
...> for i := 0; i < n; i++ {
...> for j := 0; j < n; j++ {
...> total += i ^ j
...> }
...> }
...> return total
...> }
gluon> :profile hot(30000)
cpu profile 42 samples
too few samples to draw a conclusion from — read the ranking below as a hint, not a measurement
380ms 90.48% main.hot entry 1 total += i ^ j
40ms 9.52% main.hot entry 1 for j := 0; j < n; j++ {
cpu profile $TMPDIR/gluon-session-2330176384/cpu-1790205309984019000-1.pprof
go tool pprof $TMPDIR/gluon-session-2330176384/cpu-1790205309984019000-1.pprof
gluon> func grow(n int) []string {
...> var out []string
...> for i := 0; i < n; i++ {
...> out = append(out, fmt.Sprint(i))
...> }
...> return out
...> }
gluon> :memprof len(grow(50000))
mem profile, allocated bytes 4.93MB allocated
4.90MB 99.48% main.grow entry 2 out = append(out, fmt.Sprint(i))
mem profile $TMPDIR/gluon-session-2330176384/mem-1790205311185323000-2.pprof
go tool pprof $TMPDIR/gluon-session-2330176384/mem-1790205311185323000-2.pprof

Read the sample count first. It is the number that says whether the ranking under it means anything, and for a REPL expression it often does not. Go asks for 100 samples a second, so an expression that finishes in a hundredth of a second contributes none, and the report is empty by construction. Below a hundred samples the leading share carries more than ten percent of error and can swap places between two runs of the same expression — which is why the report says so rather than letting a ranking speak for itself.

That threshold is further off than the arithmetic suggests. The loop above ran for a little over half a second — fifty-odd samples at the rate Go asks for — and 38 came back, because the rate is what the profiler asks the operating system for, not what it gets; macOS in particular delivers a fraction of it. Profile a workload, not a line, and believe the count over the clock.

A heap profile carries four measures that answer different questions, so :memprof names the one it shows — allocated bytes, which pairs with the B/op :bench prints — and leaves the other three in the file. What the summary cannot tell you, the file can: go tool pprof opens it, and -http=:0 draws the flame graph gluon does not try to. Neither command takes a port: each line is a program that runs and exits, so there is no live process to serve a profile from, and these capture one from a run that really happened instead.

What the compiler decided

builds, never runs

Escape analysis, inlining and the assembly listing are answered by the compiler itself, in its own words rather than a paraphrase. Each costs a build and never runs anything.

gluon> :esc make([]byte, 32)
make([]byte, 32) does not escape
make([]byte, 32)
^
(in this context — a value that outlives its frame escapes; one that does not, does not)
gluon> :esc fmt.Sprint(make([]byte, 32))
... argument does not escape
fmt.Sprint(make([]byte, 32))
^
make([]byte, 32) escapes to heap
fmt.Sprint(make([]byte, 32))
^
make([]byte, 32) escapes to heap
fmt.Sprint(make([]byte, 32))
^
(in this context — a value that outlives its frame escapes; one that does not, does not)
gluon> func add(a, b int) int { return a + b }
gluon> :inline add(1, 2)
inlining call to add
add(1, 2)
^
gluon> func fizzbuzz(n int) string {
...> var b strings.Builder
...> for i := 1; i <= n; i++ {
...> switch {
...> case i%15 == 0:
...> b.WriteString("FizzBuzz ")
...> case i%5 == 0:
...> b.WriteString("Buzz ")
...> case i%3 == 0:
...> b.WriteString("Fizz ")
...> default:
...> b.WriteString(strconv.Itoa(i) + " ")
...> }
...> }
...> return b.String()
...> }
gluon> :inline fizzbuzz
cannot inline fizzbuzz: function too complex: cost 262 exceeds budget 80
func fizzbuzz(n int) string {
^
gluon> :asm add
main.add STEXT size=16 align=0x0 args=0x10 locals=0x0 funcid=0x0 leaf

0x0000 00000 (entry 0 line 1) FUNCDATA $1, gclocals·g5+hNtRBP6YXNjfog7aZjQ==(SB)
0x0000 00000 (entry 0 line 1) FUNCDATA $5, main.add.arginfo1(SB)
0x0000 00000 (entry 0 line 1) FUNCDATA $6, main.add.argliveinfo(SB)
0x0000 00000 (entry 0 line 1) PCDATA $3, $1
0x0000 00000 (entry 0 line 1) ADD R1, R0, R0
0x0004 00004 (entry 0 line 1) RET (R30)
0x0000 00 00 01 8b c0 03 5f d6 00 00 00 00 00 00 00 00 ......_.........

:esc asks whether a value reaches the heap, and the answer depends on context — which the output says every time. The same 32-byte slice stays on the stack while nothing keeps it, and escapes the moment it is handed to fmt.Sprint as an any. For the flatter question, does this allocate, :bench's allocs/op is the better answer: it is measured, and context does not change it.

:inline reports, for a line, every call the compiler flattened, and for a function you declared, whether it can be inlined at all and what it costs against the budget. fizzbuzz cannot: its cost is more than three times what the compiler allows.

:asm is the listing for one function or method the session declared — F, T.M or (*T).M — with every position naming the entry it came from. Only the session's own functions: widening the listing to the standard library would recompile it under different flags and throw away the warm build cache every line depends on, so :asm strings.Index is refused with that reason rather than answered slowly. This one is arm64, because that is where it was recorded.

Vet and the race detector

:vet runs the toolchain's own analysers over the session, and :race runs one expression under the race detector.

gluon> :vet fmt.Printf("%d\n", "x")
fmt.Printf format %d has arg "x" of wrong type string
fmt.Printf("%d\n", "x")
^
gluon> func spawn() int {
...> var wg sync.WaitGroup
...> n := 0
...> wg.Add(2)
...> for i := 0; i < 2; i++ {
...> go func() { n++; wg.Done() }()
...> }
...> wg.Wait()
...> return n
...> }
gluon> :race spawn()
the instrumented standard library was compiled for this run; later :race lines reuse it
(int) 2
==================
WARNING: DATA RACE
Read at 0x00c00009c058 by goroutine 7:
main.spawn.func1()
entry 0 line 6: go func() { n++; wg.Done() }() +0x30
Previous write at 0x00c00009c058 by goroutine 8:
main.spawn.func1()
entry 0 line 6: go func() { n++; wg.Done() }() +0x40
Goroutine 7 (running) created at:
main.spawn()
entry 0 line 6: go func() { n++; wg.Done() }() +0x78
main.main()
entry 1 line 1: spawn() +0x28
Goroutine 8 (finished) created at:
main.spawn()
entry 0 line 6: go func() { n++; wg.Done() }() +0x78
main.main()
entry 1 line 1: spawn() +0x28
==================
Found 1 data race(s)

:vet reports each finding against the line you typed; with an expression, it vets the session with that line added. Findings in the code gluon generates around your lines are never shown, because there is nothing you could do about one. It vets the session, not the module you are attached to — that has its own go vet ./... — and there is no :lint, because staticcheck and its neighbours are dependencies gluon does not have.

:race is the one question here that has to run, because a data race is a runtime fact no build can be asked about. The value is printed either way: a race is something that happened during the run, not instead of it. It observes one run — finding nothing is not proof there is no race, since the detector sees one interleaving, and the output says so every time rather than implying a verdict it cannot give. The first :race in a session builds an instrumented binary beside the ordinary one, and the first on a machine compiles the race-instrumented standard library as well, which takes a few seconds; later ones reuse both.

The stack

:trace evaluates an expression and captures the stack it was evaluated on, each frame named by the session entry it came from.

gluon> func fib(n int) int {
...> if n < 2 {
...> return n
...> }
...> return fib(n-1) + fib(n-2)
...> }
gluon> :trace fib(10)
(int) 55
fib(10) the expression you traced
nothing of yours called it — gluon compiles each line into a program whose
main runs it directly, so an expression evaluated at the prompt has no
caller above it. For what a call does underneath, :save -debug writes the
module and names the command that steps through it.

It holds the expression's callers, not its callees — a function it is about to call has not been entered yet, and by the time the call returns its frame is gone. At the prompt the chain is usually one line long, and the output says why rather than showing an empty list: gluon compiles each line into a program whose main runs it directly, so there is no process to pause and no breakpoint to set. For what a call does underneath, :save -debug writes the session out as a module with a debugger launch configuration beside it, and names the command that starts one — Scratchpads has it.

Where a line's latency goes

:time on makes every line report where its latency went: gofmt, the type check, the build and the run.

gluon> :time on
timing on
gluon> strings.Repeat("ab", 3)
(string) "ababab" len=6
[goimports 11.1ms · typecheck 79.5ms · build 202.7ms · run 103.1ms · total 396.4ms]
gluon> strings.Repeat("ab")
error: not enough arguments in call to strings.Repeat
strings.Repeat("ab")
^
[gofmt 0s · typecheck 1.2ms · total 1.3ms]
gluon> :time off
timing off

The two lines are the whole design, measured. The first had to run, so it paid for the build and the run — a few hundred milliseconds, which is the price of the real compiler. The second has a type error, which the in-process checker found in about a millisecond; nothing was built. The same is true of declarations, constant expressions, and every question on the inspecting page that is marked no build. How it works has the numbers for each kind of line.
