1

What gluon found, and where

Attached to a project, the next question is usually about its data. :db says what gluon can reach and where it learned it — and until you have written that down, :query will not guess.

gluon> :db
sqlite ~/src/shop/data/shop.db
from
config.yaml database.path
data/shop.db
driver
modernc.org/sqlite a sqlite driver, in the build list
not configured — gluon init records this. It stores the name of a variable, never its value.
gluon> :query SELECT count(*) FROM users
error: no database is configured

Nothing was configured here. The settings file names data/shop.db, and the file itself is a SQLite database because its first sixteen bytes say so — so the two merge into one answer with two sources rather than two answers to choose between. Two genuinely different databases would be listed and refused, because the wrong guess here is a query against the wrong data.

A value is a database because of its shape, never because of its name. DATABASE_URL=https://api.example.com is a URL; a fixtures.db full of JSON is not SQLite. Detection reads .env, compose, config and Go files by shape, sends nothing anywhere, and opens nothing until a query runs. The driver is the one the project already requires — gluon never links one.

2

Writing it down

gluon init records the database, and what it records is a reference: where the connection lives, never what it is.

Shellfrom the project's directory
$ gluon init -no-prompt
example.com/shop
found one database:
sqlite ~/src/shop/data/shop.db
config.yaml database.path
data/shop.db
drivers in the build list
modernc.org/sqlite (sqlite)
would append to ~/.config/gluon/config.toml
[[database]]
module = "example.com/shop"
name = "primary"
driver = "sqlite"
file = "~/src/shop/data/shop.db"
nothing was written — run `gluon init` to be asked where this should go, or `gluon init -write -global` to append it.
$ gluon init -no-prompt -write -local
example.com/shop
found one database:
sqlite ~/src/shop/data/shop.db
config.yaml database.path
data/shop.db
drivers in the build list
modernc.org/sqlite (sqlite)
wrote ~/src/shop/gluon.toml
[[database]]
name = "primary"
driver = "sqlite"
file = "data/shop.db"
gluon -host . then :db
$ cat gluon.toml

gluon does not store passwords. It stores the name of the variable, or the file and key, that a connection string lives in, and reads the value when a query runs — so the config is safe to read, to share and to commit, and the loader refuses a dsn that carries a password inline. A SQLite file inside the project is named relative to gluon.toml, so the file still points at it after the project moves.

Nothing is written without being asked. -no-prompt prints the block and stops; gluon init on its own asks where it should go; writing without the question takes -write and either -local — ./gluon.toml, which travels with the project and may set only [[database]] and imports — or -global, your own config. The nearest gluon.toml wins over the global config, and the two are never merged, because a half-merged database configuration is untraceable.

3

Querying it

:query runs one statement against the configured database, through the project's own driver.

gluon> :db
databases 1 configured
╭─────────┬────────┬─────────────────────────┬───────────┬───────╮
│ name │ driver │ target │ mode │ │
├─────────┼────────┼─────────────────────────┼───────────┼───────┤
│ primary │ sqlite │ ~/src/shop/data/shop.db │ read-only │ ready │
╰─────────┴────────┴─────────────────────────┴───────────┴───────╯
from ~/src/shop/gluon.toml
gluon> :query SELECT id, email, plan FROM users ORDER BY id LIMIT 5
╭────┬───────────────────────┬──────╮
│ id │ email │ plan │
├────┼───────────────────────┼──────┤
│ 1 │ ada@example.com │ free │
│ 2 │ grace@example.com │ free │
│ 3 │ katherine@example.com │ pro │
│ 4 │ margaret@example.com │ free │
│ 5 │ hedy@example.com │ free │
╰────┴───────────────────────┴──────╯
5 rows · ~/src/shop/data/shop.db
gluon> :query SELECT plan, count(*) AS customers FROM users GROUP BY plan ORDER BY customers DESC
╭──────┬───────────╮
│ plan │ customers │
├──────┼───────────┤
│ free │ 274 │
│ pro │ 138 │
│ team │ 68 │
╰──────┴───────────╯
3 rows · ~/src/shop/data/shop.db
gluon> :query UPDATE users SET plan = 'team' WHERE id = 1
error: UPDATE is not a read-only statement — :query -w UPDATE users SET plan = 'team' WHERE id = 1 runs it anyway.
The check is on the first word, not a parse: it is here to catch the paste you did not mean, not to prove a statement is safe
gluon> :query -w UPDATE users SET plan = 'team' WHERE id = 1
no rows
0 rows · ~/src/shop/data/shop.db
gluon> :query SELECT id, email, plan FROM users WHERE id = 1
╭────┬─────────────────┬──────╮
│ id │ email │ plan │
├────┼─────────────────┼──────┤
│ 1 │ ada@example.com │ team │
╰────┴─────────────────┴──────╯
1 row · ~/src/shop/data/shop.db

A read runs inside a read-only transaction, which is a guarantee the server enforces rather than one gluon claims; when a driver has no such thing the answer says so. Anything else needs :query -w, and the check in front of it is on the first word — a keyword check, there to catch the paste you did not mean, not to prove a statement safe. A write runs as written, outside any transaction, and :query reports what a statement returned: an UPDATE returns no rows, so the SELECT after it is how you see what changed.

A cell that was SQL NULL and a cell holding the text NULL are different answers, so the text is quoted, and the distinction survives a pipe that has stripped the colour. :query -json answers with the same rows in a shape a program reads — a NULL is JSON null, every other cell is text as the driver scanned it, type is what the database declared, and truncated says whether the fetch cap bound. :query -d picks a database by name when a project configures several.

A query is never answered from cache. gluon caches results by program text, which is right for :undo and wrong for a database: the same SELECT count(*) twice would report the count from when you first asked. :migrations reads a migration library's tracking table through the same connection — Plugins has it.

4

What it will not do

The whole trust model
  • No connection string on a command line: there is no -dsn and no :db connect <url>, because either would put a password in a history file.
  • No password in a config gluon writes, and none accepted inline in one it reads.
  • No connection string in the generated program: it reaches the child through its environment, and the password lives in an unexported field whose printed form is always the redacted one, so %v, a log line or -json cannot leak it.
  • No guess between two databases, and no driver linked into gluon.
