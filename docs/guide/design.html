1

Why it is not an interpreter

gluon compiles with your real Go toolchain. Every line re-renders the whole session into a genuine Go program and builds it, so the semantics are the compiler's — not an interpreter's approximation of them.

The alternative was embedding an interpreter, and the mature ones lag the language: yaegi's standard library tables target Go 1.21 and 1.22, and gomacro does not import generic standard library functions at all, which breaks slices.Sort and maps.Keys — most of modern Go. If you are using a REPL to learn the language, semantics that quietly differ from the compiler teach you wrong Go.

The cost is latency, and most lines do not pay it. Before anything is built, the session is type-checked in gluon's own process, from export data, in about a millisecond — so a type error, a declaration, a constant expression, and every question marked no build on the inspecting page never reach the toolchain. The checker is never an authority: when it cannot answer, the compiler is asked, and GLUON_NO_TYPECHECK=1 turns it off entirely.

2

Where a line's time goes

:time shows it for every line: a declaration and a constant answered by the checker, a type error answered by it, and a value that had to run.

PhaseCost, measured on darwin/arm64
type check, in process, warmabout 1ms

The first row is why a type error comes back in a millisecond and a value in a third of a second. The first check of a session is slower — it loads export data — and the first line to name a package pays for goimports once. The exec row is macOS validating a binary it has never seen; Install has how to remove it, and gluon doctor measures it. An attached project costs nothing a line: gluon always builds its own one-file module, and the toolchain loads the import graph, not every package the project has.

3

Replay, and what it costs

A Go program cannot be paused and resumed between lines, so gluon does not try: each line is a whole program, built from every entry so far, and run from the start. Output from the entries before the newest is muted at the file-descriptor level, so you see only the newest line's.

That is what makes the semantics the compiler's, and it has one honest cost: side effects repeat. A request made on line three is made again on every line after it; a file is written again; time.Now() moves. Muting rather than diffing is what keeps a program that ranges over a map readable — a diff breaks the moment the order changes — but the re-execution is real. :pin takes an entry out of the replay, :undo takes it out of the session, and The session shows both.

Two things follow from each line being a program that exits: there is no process to attach a debugger to or serve a live profile from, which is why :profile captures one from a run that happened and :save -debug hands you a real module; and a goroutine is waited for only briefly, and said.

4

How it compares

gore is the closest relative — also a real-toolchain REPL, mature and MIT-licensed, with gopls-backed completion. The differences are the reasons gluon exists. gore pays a full go run round trip for every line, including the ones that only needed a type error; gluon type-checks in process and answers errors, :t, :m, :layout and constants in about a millisecond. gore prints replayed output again on every evaluation; gluon mutes it, which is what keeps non-deterministic programs readable. And gluon carries the parts of pry Go never had — it, :doc -src, a value printer that tells the truth about identity — plus attachment that reaches internal/ packages, the database layer and the plugins. Lines that actually run cost about 300ms in both: that is the price of the real compiler, and neither can cheat it.

yaegi and gomacro are a different premise — interpreters: fast, with the interpreter's semantics rather than the compiler's. gophernotes is a Jupyter kernel over gomacro, the same trade behind a different surface; gluon is a terminal tool, not a kernel. None of the three has an agent surface. gluon mcp serves the millisecond inspectors to a coding agent, so it measures method sets, layouts and benchmarks instead of guessing.

5

What it never does

Promises the code keeps
  • Never writes into your project. It builds in its own temp module, so it can never leave a stray binary in your repository, and a line runs in the session's directory, not yours.
  • Never edits your go.mod. A module added with :get belongs to the session.
  • Never reaches the network on its own account except :get, which fetches a module, and :share, which uploads and asks every time. A line can make its own requests, as any Go program can.
  • Never stores a password, and never puts a connection string in a program it generates.
  • Never guesses between two answers — two databases, two of your project's packages with one name — when the wrong guess would look like a right one. It lists them and asks.

The reasoning behind each of these, and the invariants the code is held to, are in the project's ROADMAP.md.
