1

One-shots and pipes

gluon -e is the ruby -e shape: evaluate, print, exit. It takes Go and meta commands alike, so every inspector is a shell one-liner, and a pipe into gluon is the same engine with no banner.

Shellfrom a shell
$ gluon -e 'strings.ToUpper("hi")'
(string) "HI" len=2
$ gluon -e 'x := 21' -e 'x * 2'
(int) 42
$ echo 'strings.Repeat("ab", 3)' | gluon
(string) "ababab" len=6
$ gluon -e '[]int{1, 2, 3}' -json
{
"ok": true,
"values": [
{
"type": "[]int",
"kind": "list",
"text": "([]int) [1 2 3] len=3 cap=3",
"len": 3,
"cap": 3
}
],
"exitCode": 0
}
$ gluon -e ':layout struct{ a bool; b int64; c bool }' -json
{
"ok": true,
"command": ":layout",
"text": "struct{a bool; b int64; c bool} 24 bytes, align 8\n 0 a bool 1\n (7 bytes padding)\n 8 b int64 8\n 16 c bool 1\n (7 bytes padding)\n reordering as b, a, c would be 16 bytes — 8 saved"
}
$ gluon -e 'strings.Repeat("ab")'; echo "exit $?"
not enough arguments in call to strings.Repeat
strings.Repeat("ab")
^
exit 1

Repeated -e arguments land as one batch — one build — and every expression that prints, prints. A compile error goes to the terminal as it would at the prompt and the exit status says it failed, so a script can tell. None of it opens a scratchpad: a one-shot can neither inherit nor change the session you have open elsewhere.

What a script reads is the plain form, one line per value, and it is a compatibility surface: no setting reaches it — not value.form, not a theme, not a plugin's renderer — so a script written against it keeps working. Rendering has the difference.

2

JSON, for a program to read

-json prints one object instead of the plain rendering. An evaluation answers with its values, each with its type, kind and text; a meta command answers with ok, the command, and its text.

Every envelope carries ok, and an error comes back as JSON on standard output too, so nothing has to read standard error to find out what happened. ok says the command did its job, not what it found: an :impl that answers no is still ok, so a check reads the text. :query -json answers with rows a program can read, and gluon doctor -json and gluon init -json answer with reports. The envelopes are compatibility surfaces, held to their shape by gluon's own tests.

3

Against a project

-host . attaches a one-shot to the module you are standing in, the way it attaches the REPL. The attach line goes to standard error, so standard output is only what the line printed.

Shellin ~/src/shop
$ gluon -host . -e ':layout pricing.LineItem'
attached to example.com/shop (go 1.26.0) at ~/src/shop
pricing.LineItem 56 bytes, align 8
0 Gift bool 1
(7 bytes padding)
8 Qty int64 8
16 Taxable bool 1
(7 bytes padding)
24 SKU string 16
40 Price decimal.Decimal 16
reordering as SKU, Price, Qty, Gift, Taxable would be 48 bytes — 8 saved
$ gluon -host . -e 'pricing.Total(pricing.Sample()).String()'
attached to example.com/shop (go 1.26.0) at ~/src/shop
(string) "56.14" len=5
4

In CI

Because the inspectors are one-liners with a stable output, a build can hold a property the compiler does not: that a hot struct stays packed, that a type keeps satisfying an interface, that a function stays inlinable.

justfilea struct that must not grow
# fails while reordering the fields would save bytes
check-layout:
    gluon -host . -e ':layout pricing.LineItem' -json \
      | jq -e '.text | test("reordering") | not'

# fails the day the service stops satisfying its generated interface
check-orders:
    gluon -host . -e ':impl *rpc.Orders, shopv1.OrdersServer' -json \
      | jq -e '.text | test("does not implement") | not'

A one-shot pays for the toolchain like any line that runs — a few hundred milliseconds warm — and the inspectors answered by the type checker pay for none of it. gluon doctor in a CI job reports the toolchain and module it found, and exits non-zero only when something gluon depends on is broken.
