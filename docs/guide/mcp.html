1

Why a coding agent wants it

gluon mcp serves the session's inspectors to a coding agent over the Model Context Protocol, on standard input and output. The questions agents otherwise answer by guessing — what is in this method set, does this type satisfy that interface, how is this struct laid out, what does this benchmark say — become tools answered by the toolchain that builds your code.

Most of the static tools answer from the type checker, in about a millisecond each, so an agent can ask dozens of them in the time one build takes. Each tool's description carries the command's synopsis, flags and examples, written the way the tool takes them — :help's page, for the reader that never skims.

2

Setting it up

Any MCP client that runs a server over stdio can run gluon. The server is the gluon binary with the mcp argument.

JSON.mcp.json, in a project
{"mcpServers": {"gluon": {"command": "gluon", "args": ["mcp"]}}}
ShellClaude Code, from the project's directory
claude mcp add gluon -- gluon mcp

When the working directory is inside a Go module, the session attaches to it — internal/ packages included — because installing the server in a project's config is the asking. -host picks a different module, and -host off serves a standalone session. Like gluon -e, the server opens no scratchpad, so an agent's calls can neither inherit nor change the session you have open.

3

Two tiers, and who chooses

15 static18 with --eval

By default the server offers only the tools that run nothing: the type and method-set questions, the interface questions, layout, scope, documentation, mocks and spies. The tools that run code — evaluation, benchmarks, the profilers, the race detector, the plugin commands — exist only behind --eval.

JSONwith evaluation enabled
{"mcpServers": {"gluon": {"command": "gluon", "args": ["mcp", "--eval"]}}}

Granting execution belongs to the person who edits the client's config, not to the agent — which is why it is a flag in that config and not a tool the agent can call. With --eval, evaluation replays the whole session on each call, exactly as the prompt does, so side effects repeat; the tool descriptions say so. A flag that runs code at the prompt, like :t -d, is ignored by the static tool it belongs to. The MCP reference lists every tool with its description and schema, exactly as a client receives them.

4

Long answers

Every tool takes an optional offset and limit, counted in lines of the answer, so a client with a small window asks for the part it can hold and is told which lines it got and how many there are.

Leave both out and the answer is the whole one, byte for byte what the prompt prints through a pipe. An answer is plain text — the same bytes gluon -e would print — with no colour and no view, so a client never has to strip anything.
