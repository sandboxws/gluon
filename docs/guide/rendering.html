Five shapes for a value

A value with structure is drawn as a bordered table by default, and a scalar stays on its line. A table is one crushed column for a list of structs, though, and past its first level a cell truncates — so there are five shapes, and value.form chooses.

gluonone value, five ways
gluon> type Point struct{ X, Y int }
gluon> pts := []Point{{1, 2}, {3, 4}, {5, 6}}
gluon> pts
([]main.Point) len=3 cap=3
╭───┬───────────╮
│ # │ value │
├───┼───────────┤
│ 0 │ {X:1 Y:2} │
│ 1 │ {X:3 Y:4} │
│ 2 │ {X:5 Y:6} │
╰───┴───────────╯
gluon> :settings value.form columns
value.form is columns · default = "columns" in ~/.config/gluon/config.toml
gluon> pts
([]main.Point) len=3 cap=3
╭───┬───┬───╮
│ # │ X │ Y │
├───┼───┼───┤
│ 0 │ 1 │ 2 │
│ 1 │ 3 │ 4 │
│ 2 │ 5 │ 6 │
╰───┴───┴───╯
gluon> :settings value.form tree
value.form is tree · default = "tree" in ~/.config/gluon/config.toml
gluon> map[string][]int{"odd": {1, 3}, "even": {2, 4}}
(map[string][]int) len=2
├──"even" []int len=2 cap=2
│ ├──0 2
│ └──1 4
└──"odd" []int len=2 cap=2
├──0 1
└──1 3
gluon> :settings value.form literal
value.form is literal · default = "literal" in ~/.config/gluon/config.toml
gluon> pts
[]Point{Point{X: 1, Y: 2}, Point{X: 3, Y: 4}, Point{X: 5, Y: 6}} len=3 cap=3
gluon> :settings value.form line
value.form is line · default = "line" in ~/.config/gluon/config.toml
gluon> pts
([]main.Point) [{X:1 Y:2} {X:3 Y:4} {X:5 Y:6}] len=3 cap=3
gluon> :settings value.form -
value.form is back to table · dropped default = "line" from ~/.config/gluon/config.toml

columns gives a list of structs a column per field. tree recurses where a table cell truncates, and is the only shape that shows nesting all the way down. line keeps a value on one line however deep it goes. literal answers a different question: it is the value as Go source you could paste back — into a test, say — and a value with no literal form, such as a channel or a func, falls back to a line and names the part that has none.

A kind can take its own shape over the one everything else takes: value.form.list, value.form.map and value.form.struct. :settings value.form - puts the default back. A change takes effect on the next line, and it is written into config.toml, so the next session draws the same way — Configuration has the rest of :settings.

Cycles, sharing, and what a value hides

Values that point at each other are described as what they are. A cycle is labelled where it closes, and an object that appears twice is labelled rather than printed twice as though it were two.

gluon> type Node struct{ Val int; Next *Node }
gluon> a := &Node{Val: 1}
gluon> b := &Node{Val: 2, Next: a}
gluon> a.Next = b
gluon> a
(*main.Node) #1&
╭───────┬──────────────────────────╮
│ field │ value │
├───────┼──────────────────────────┤
│ Val │ 1 │
│ Next │ &{Val:2 Next:<cycle #1>} │
╰───────┴──────────────────────────╯
cyclic — it is reachable from inside itself
gluon> type P struct{ X int }
gluon> p := &P{1}
gluon> []*P{p, p}
([]*main.P) len=2 cap=2
╭───┬─────────────╮
│ # │ value │
├───┼─────────────┤
│ 0 │ #2&{X:1} │
│ 1 │ <shared #2> │
╰───┴─────────────╯
the same object appears more than once — not a copy
gluon> fmt.Errorf("layer2: %w", fmt.Errorf("layer1: %w", os.ErrNotExist))
(*fmt.wrapError) &
╭───────┬─────────────────────────────────────────────────────────────────────╮
│ field │ value │
├───────┼─────────────────────────────────────────────────────────────────────┤
│ msg │ "layer2: layer1: file does not exist" │
│ err │ &{msg:"layer1: file does not exist" err:&{s:"file does not exist"}} │
╰───────┴─────────────────────────────────────────────────────────────────────╯

Sharing and cycles are different lessons, so they read differently: a cycle would not terminate if it were printed naively, while sharing does terminate but hides that changing the object through one name changes it through the other. A label appears only on an object something actually points at, so an ordinary value is unchanged.

Unexported fields that hold a struct, a slice or a map are described rather than left out, which is what makes a %w chain visible at all — fmt's %+v reads the same fields, flattened. GLUON_NO_UNSAFE=1 turns it off. The program gluon builds only describes a value, as JSON; everything you see is drawn by gluon's own process, which is why the generated code stays standard library and every line builds as fast as it can.

3

How much of a value you see

The program that describes a value stops somewhere: at 200 elements of any one collection, and at 6 nested levels. value.items and value.depth move those, from the next line.

Both reach the program through its environment, never through its source, so the source is the same at every setting and an :undo across a change still finds its cached result. They are also GLUON_MAX_ITEMS and GLUON_MAX_DEPTH, which a shell can export for every session; gluon doctor says when either is set. A separate budget bounds the whole value — it is what keeps one *http.Request from becoming a dump of its transport — and neither setting moves it, so a collection of large elements can stop short of the number asked for, and says so when it does.

A view that scrolls

:inspect opens the one thing a printed table cannot be: a view that scrolls, over a large value. j/k move, / filters, q closes.

gluon480 rows
gluon> type User struct{ ID int; Name, Email string }
gluon> users := make([]User, 480)
gluon> for i := range users { users[i] = User{i, fmt.Sprintf("user%03d", i), fmt.Sprintf("user%03d@example.com", i)} }
gluon> len(users)
(int) 480
gluon> :inspect usersopens a view
([]main.User) len=480 cap=480
╭────┬────────────────────────────────────────────────────╮
│ # │ value │
├────┼────────────────────────────────────────────────────┤
│ 0 │ {ID:0 Name:"user000" Email:"user000@example.com"} │
│ 1 │ {ID:1 Name:"user001" Email:"user001@example.com"} │
│ 2 │ {ID:2 Name:"user002" Email:"user002@example.com"} │
│ 3 │ {ID:3 Name:"user003" Email:"user003@example.com"} │
│ 4 │ {ID:4 Name:"user004" Email:"user004@example.com"} │
│ 5 │ {ID:5 Name:"user005" Email:"user005@example.com"} │
│ 6 │ {ID:6 Name:"user006" Email:"user006@example.com"} │
│ 7 │ {ID:7 Name:"user007" Email:"user007@example.com"} │
… 44 more lines

The view takes the whole screen, which the rest of gluon never does, so it keeps one rule: it prints nothing while it is up, and leaves exactly one line behind when it closes — []main.User 200 rows browsed — so scrollback stays a complete transcript. What it browses is what the value printer described: 200 elements unless you ask for more, and :inspect -n asks for this one view without moving value.items. Through a pipe there is no view, and :inspect prints the ordinary rendering above instead, so nothing is lost.

:src, :doc, :settings and a long :help page open the same kind of view once their output outgrows a screen, and print in full through a pipe.

5

What a pipe gets

Everything on this page is what a terminal draws. A pipe, gluon -e and the -json envelopes get one plain line per value, whatever the settings say — those are surfaces scripts read, and no setting reaches them.

Shellthe same bytes whatever value.form says
$ gluon -e '[]int{3, 1, 2}' | cat
([]int) [3 1 2] len=3 cap=3

Plugin renderers — a uuid.UUID as a UUID, a sql.NullString as NULL — are terminal-only for the same reason. Scripting covers what the plain and JSON forms promise.
