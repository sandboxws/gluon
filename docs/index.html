gluon

A REPL and scratch runner for Go, for when you want to check what s[i] prints without writing a main package first. Every line re-renders the whole session into a genuine Go program and compiles it with your real toolchain — so nothing here can teach you Go that the compiler disagrees with.

01

Install

Go 1.27+macOS · Linux · WSLv0.1.0

gluon is one binary and no daemon. It needs a Go toolchain on PATH, because the toolchain is the evaluator — there is nothing to install alongside it.

Shellno clone needed
go install github.com/sandboxws/gluon/cmd/gluon@latest

Or brew install sandboxws/tap/gluon, or a binary from the releases page.

Shellverify, and start
gluon doctor                   # what gluon can see from here
gluon                          # and you are in

The first guide has the rest: where the binary lands, shell completion and a man page, and the 105ms of every line that macOS adds and you can take back.

The first five minutes

Start here

Type Go. gluon writes the import lines, silences the errors Go raises about scratch code, and prints the value with its type and the facts about it you would otherwise print a second time.

gluona value, and the truth attached to it
gluon> x := []int{3, 1, 2}
gluon> slices.Sort(x)
gluon> x
([]int) len=3 cap=3
╭───┬───────╮
│ # │ value │
├───┼───────┤
│ 0 │ 1 │
│ 1 │ 2 │
│ 2 │ 3 │
╰───┴───────╯
gluon> "héllo"[1]
(uint8) 195 (0xc3)
gluon> "héllo"
(string) "héllo" len=6 bytes, 5 runes

Nothing in that session imports slices, and nothing uses x after declaring it — Go rejects both, and a REPL that made you write them would be a worse REPL. Errors and panics name the line you typed, not a file under a temp directory:

gluon> x := []int{1, 2, 3}
gluon> func f(a int) int {
...> return a + bogus
...> }

return a + bogus
^
gluon> x[10]

goroutine 1 [running]:
main.main()
x[10] +0x24
[exit status 2]
gluon> :undo
undone (1 entry left)
gluon> len(x)
(int) 3

The first five minutes goes on from here: it and _N, pasting a block, and help for every command.

05

Why it isn't an interpreter

The premise

This is the decision everything else falls out of. gluon compiles with your real Go toolchain; it does not embed a second implementation of Go that can disagree with the first.

The alternative was embedding an interpreter, and both mature ones lag the toolchain badly: yaegi's stdlib symbol tables target Go 1.21/1.22, and gomacro does not import generic stdlib functions at all — which breaks slices.Sort and maps.Keys, i.e. most of modern Go.

The argument in one line

If you are using a REPL to learn the language, semantics that quietly differ from the compiler teach you wrong Go.

The cost is latency, and most lines do not pay it. gluon type-checks in its own process first, in about a millisecond — so a type error, a declaration, a constant expression and every :t or :m never reach the toolchain at all. :time on shows where each line's time went:

gluon> :time on

gluon> type Point struct{ X, Y int }

gluon> 1 << 20

[gofmt 100µs · typecheck 1.1ms · total 1.2ms]
gluon> strings.Repeat("ab")

strings.Repeat("ab")
^
[goimports 11.8ms · typecheck 69.2ms · total 81ms]

The type checker is deliberately never an authority: when it cannot answer, the compiler is asked, and GLUON_NO_TYPECHECK=1 turns it off entirely. How it works has the rest.

How it compares

gore is the closest relative — also a real-toolchain REPL, mature and MIT-licensed, with gopls-backed completion. The differences are the reasons gluon exists.

gluongoreyaegi · gomacro
Semanticsthe compiler'sthe compiler'san interpreter's
A type error~1ms, no builda full go runfast
Replayed outputmutedprinted again—
Your project's internal/imports——
Database, pluginsyes——
A coding agentgluon mcp——

Lines that actually run cost about 300ms in both gluon and gore: that is the price of the real compiler, and neither can cheat it. gophernotes is a Jupyter kernel over gomacro — the same trade behind a different surface; gluon is a terminal tool, not a kernel.

07

The honest limitation

Read this:pin is the defence

Every line replays the entire session, so side effects repeat: an HTTP call fires again, a file gets written again.

Output from replayed entries is muted at the file-descriptor level — not diffed, because diffing breaks the moment a program ranges over a map — so you only ever see the newest line's output. But the re-execution is real.

Figureevery column is one line you typed · toggle the pin and watch the call count
runs, and prints runs — output muted as replay declaration: built, not run pinned: not in the program

Four lines typed, and the http.Get on entry 2 has fired three times — once when you typed it, and once more for each line after it. :pin takes an entry out of the program — you are saying it has already happened — and gluon refuses rather than guesses when a later line needs what the pinned one bound. The session works it through.

The general rule

Where gluon differs from a real main, it tells you in the output rather than hiding the difference — the same instinct behind refusing an interpreter, and refusing to guess.
